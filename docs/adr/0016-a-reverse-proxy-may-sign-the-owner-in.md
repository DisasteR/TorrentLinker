# A reverse proxy may sign the owner in

The Web UI asks for its own password. Owners who already run a reverse proxy that signs users in, through forward auth to an identity provider such as Authentik or through basic auth, sign in twice and keep one more password. Turning the Web UI password off would leave the server open to anyone who reaches its port without passing the proxy, through a published port, a shared Docker network or the LAN.

`TL_WEB_AUTH=proxy` replaces the Web UI password with a list of trusted proxy networks, `TL_TRUSTED_PROXIES`. The server refuses to start in this mode without that list. A request from a listed address acts as the owner; any other address gets `403`, not `401`, so it is not taken for an expired Web UI session. The check reads the connection's own address: forwarded headers are ignored (`proxy_headers=False`), so a client cannot claim to be the proxy. A header naming the signed-in user would prove nothing more for the same reason, so none is required.

The check replaces the Web UI session exactly where the session applied: `/api/` and `/documentation/`. The browser request header still guards mutations, since the proxy's own sign-in is usually a cookie too. Agents (`/mcp`) and the browser companion keep their own tokens and may be routed around the proxy's sign-in, by their exact paths: an owner route must never be added under `/api/companion/`. Known limit: anything else that can connect from a trusted address is the owner, so the list should name the proxy's address, not its network, and every container on the proxy's network is inside the trust boundary. The mode depends on no particular proxy; `deploy/compose.traefik.yaml` is one example, for Traefik.
